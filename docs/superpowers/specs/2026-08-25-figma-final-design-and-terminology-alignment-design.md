# Figma 최종 디자인 반영 및 용어 정리

상태: 설계 확정, 구현 대기
작성일: 2026-08-25

## 1. 배경

디자이너가 Figma(`유니톤` 파일, "플로우차트 & 와이어프레임" + "템플릿 : 카드뉴스/랜딩페이지" 페이지) 작업을 거의 마무리했다고 전달했다. 현재 구현(2026-08-24 Figma 정합화 작업 기준)과 최신 Figma를 다시 대조한 결과, 화면 구조는 대부분 일치하지만 다음 세 영역에서 실질적인 차이가 확인됐다:

1. 리포트 화면이 이전에 의도적으로 배제했던 광고 지표·이메일 수집 형태를 다시 보여준다.
2. 대시보드 카드 비주얼과 CTA 문구가 다르다.
3. 화면 곳곳에서 "캠페인"과 "프로젝트" 용어가 혼용되고 있다("전체 프로젝트" 대시보드가 "캠페인 만들기" 버튼으로 이어짐).

이 문서는 위 차이를 사용자와 대화로 확정한 결정에 따라 구현 가능한 설계로 정리한다.

## 2. Figma 대조 결과

### 2.1 `1. 메인페이지`

- 카드가 아이콘 기반 비주얼(문서→화살표→이미지 아이콘, sparkle)과 `10시간 남음` 배지, 진행률 바로 구성됨. 카드 내용은 전부 "예시 프로젝트" 플레이스홀더.
- 기본 CTA: `+ 광고 만들기`.
- 상단 내비게이션이 "wanted" 채용 플랫폼 헤더(채용/커리어/소셜/이력서/프리랜서 메뉴)로 되어 있다. "템플릿 : 카드뉴스/랜딩페이지" 페이지의 카드에는 "Market Valley" 브랜드 배지가 별도로 존재해, `wanted` 헤더는 디자이너가 시작점으로 삼은 템플릿의 잔재로 판단했다. **결정: 현재 `SiteHeader`(marketvalley 브랜드) 유지, `wanted` 헤더는 따르지 않는다.**

### 2.2 `2-1. 온보딩` / `2-2. 온보딩`

- 헤딩 문구("제품을 만들게 된 배경을 입력해주세요", "어떤 솔루션을 제공할 예정인가요?")가 현재 구현과 완전히 일치한다.
- 예시 본문 플레이스홀더 텍스트는 다르지만(범용 "예비창업가" 예시 vs 현재 "카페 사장님" 예시), 기능적 차이는 아니다.
- 2단계 버튼 라벨이 Figma는 `다음`, 현재 구현은 `캠페인 만들기`(→ `프로젝트 만들기`로 변경 예정, §5 참고)이다.

### 2.3 `3. 진행 상황 페이지`

- 4단계 스테퍼 라벨(`접수`/`준비 중`/`수집 중`/`결과 도착`)이 이미 정확히 일치한다.
- 헤드라인/서브헤드 문구가 다르다: Figma `광고 검증을 준비하고 있습니다` / `검토한 내용을 바탕으로 광고 소재와 랜딩페이지를 제작하고 있습니다` vs 현재 `시장검증 캠페인을 준비하고 있어요` / `같은 가설로 모든 결과물을 맞추고 있어요`.
- ETA 배지가 Figma는 `결과 도착까지 2일`이다. **이건 2026-08-24 설계에서 이미 검토되고 데모 트랙에서는 따르지 않기로 확정된 사항이다(`docs/architecture.md` "진행 상황 화면" 섹션). 이번 작업에서 재검토하지 않는다 — 배지 동작(~2초 자동 진행)은 그대로 두고 헤드라인/서브헤드 문구만 갱신한다.**

### 2.4 `4. 리포트 페이지`

가장 큰 차이. Figma는 실제 Meta 광고 스타일 화면이다:

- 상태 배지: `시장성 적당함`
- 지표 카드 3개: 노출 수(`1,800,820회`), CTR(`12.6%`), 예약률(`1.5%`) — 각각 "업계 평균 대비 X% 낮음/높음" 배지 포함
- 퍼널 막대 그래프: 노출 → 클릭 → 랜딩 페이지 방문 → 예약, 각 단계 숫자 표시
- SNS 카드뉴스 소재 / 랜딩페이지 미리보기 카드 2개
- **예약자 리스트**: 이메일 주소 목록 테이블
- 하단 CTA: `다음 캠페인 만들기`(→ `다음 프로젝트 만들기`)

이 화면은 2026-08-24 설계(`2026-08-24-figma-alignment-and-dependency-split-design.md` §2)에서 "개인정보 없는 선택형 응답 계약과 충돌해 사용하지 않는다"고 명시적으로 배제했던 바로 그 화면이다. `docs/decisions/0001-close-the-validation-loop.md`, `docs/decisions/0006-publish-without-output-review-screens.md`, `docs/spec.md`("예약률이라는 명칭을 사용하지 않는다")가 전부 이 배제를 근거로 삼고 있다.

**사용자와 확인한 결과: 이번에는 디자이너 방향을 따른다.** 즉 위 결정들을 뒤집는다 — §3, §7에서 상세화한다.

### 2.5 `템플릿 : 카드뉴스/랜딩페이지`

카드뉴스 후킹 문구 배리에이션(`표지 31/32/34`) 다수가 있다. 이건 카피 톤 참고 자료 성격이 강하고 1:1로 옮길 고정 템플릿은 아니라고 판단해 이번 범위에서는 참고만 하고 구조 변경은 하지 않는다.

## 3. 이번에 확정한 결정

### 3.1 리포트 화면 지표 — 고정 데모 값, 실제 추적 아님

- `CampaignSpec`에 데모 전용 고정 지표 블록을 추가한다(§6). 값은 `decisionRule`과 같은 성격의 시스템 상수이지 AI가 생성하지 않는다(spec.md §7 "확인되지 않은 숫자를 만들어내지 않는다"와 충돌하지 않도록, AI 생성 경로에서 만들지 않고 fixture/레퍼런스 템플릿에 고정값으로 박아 넣는다).
- 실제 Meta 픽셀·페이지뷰·클릭 추적 인프라는 만들지 않는다. 화면에는 기존 "데모 데이터" 표시 관례를 그대로 적용한다.
- 인터페이스는 나중에 실제 추적으로 교체 가능하도록 값을 CampaignSpec이 아니라 별도 조회 가능한 필드로 분리한다(§6) — 사용자가 "일단 고정 데모, 나중에 직접 실제 추적 가능하게" 만들 계획이라고 밝혔다.

### 3.2 이메일 수집 — 선택적, 추가적 필드

- 공개 랜딩(`/p/[slug]`)에서 기존 3지선다 응답(긍정/중립/부정) 제출 뒤, 선택적으로 이메일을 남길 수 있는 단계를 추가한다.
- 이메일은 실제 알림/예약 발송에 쓰이지 않는다 — 리포트 화면에 "예약자 리스트"로 보여주기 위한 단순 수집·표시 용도다.
- `SignalInput`에 `email?: string`을 추가하는 **추가적(additive) 확장**으로 구현한다. 기존 익명 신호 응답 경로(이메일 없이 제출)는 그대로 유지되어 깨지지 않는다.
- 개인정보 관련 원칙 변경: `spec.md`의 "P0에서는 이메일, 이름, 전화번호 등 개인정보를 받지 않는다"는 더 이상 사실이 아니게 된다 — §7 문서 갱신 목록에서 수정한다.

### 3.3 용어 통일 — "프로젝트", 화면 문구만

- 사용자에게 보이는 명사를 전부 "프로젝트"로 통일한다: `캠페인 만들기` → `프로젝트 만들기`, `+ 새 캠페인` → `+ 새 프로젝트`, 리포트의 `· DEMO CAMPAIGN` → `· 데모 프로젝트`, `다음 캠페인 만들기` → `다음 프로젝트 만들기` 등.
- **코드 심볼(타입 `CampaignSpec`, 인터페이스 `CampaignGenerator`/`CampaignRepository`, 라우트 `/campaigns/[id]`, 컴포넌트 파일명 `campaign-wizard.tsx`/`campaign-report.tsx`)은 바꾸지 않는다.** 화면 문구만 바꾸는 범위로 한정해 위험과 작업량을 낮춘다.
- Figma의 대시보드 CTA 문구 `+ 광고 만들기`는 따르지 않는다 — "캠페인/광고/프로젝트" 세 단어가 섞이는 걸 피하기 위해 통일한 "프로젝트"를 우선한다.

### 3.4 대시보드 카드 비주얼

- 카드 시각 스타일(아이콘, 배지, 진행률 바)은 Figma를 따른다.
- 카드 내용(프로젝트명, 상태)은 Figma의 플레이스홀더("예시 프로젝트")가 아니라 현재 구현의 실제 데모 콘텐츠(마감한입 등)를 유지한다.

### 3.5 헤더 — marketvalley 브랜드 유지

Figma 플로우 프레임의 "wanted" 헤더는 템플릿 잔재로 판단하고 따르지 않는다. 현재 `SiteHeader`(marketvalley 로고 + 프로젝트/캠페인 만들기/데모 리포트 내비게이션)를 유지한다.

## 4. 이번 범위에 만들지 않을 것

- 실제 Meta 픽셀/광고 API 연동 — 지표는 고정 데모 값
- 실제 이메일 발송/알림 — 수집·표시만
- 카드뉴스 후킹 문구 템플릿의 1:1 이식 — 참고만
- 코드 심볼·라우트 리네이밍(`Campaign*` → `Project*`) — 화면 문구만
- `docs/decisions/0003`(Meta 자동화 단계) 재검토 — 이번 변경과 무관

## 5. 화면별 변경 사항

### `/` (대시보드)

- 프로젝트 카드: 아이콘/배지/진행률 바 비주얼로 교체, 콘텐츠는 유지
- CTA: `+ 새 캠페인` → `+ 새 프로젝트`

### `/new` (온보딩)

- 2단계 버튼: `캠페인 만들기` → `프로젝트 만들기`
- 헤딩·본문은 변경 없음

### `/campaigns/[id]/progress`

- 헤드라인: `시장검증 캠페인을 준비하고 있어요` → `광고 검증을 준비하고 있습니다`(Figma 문구 반영, 워딩은 구현 시 마지막으로 자연스럽게 다듬는다)
- 서브헤드: Figma 문구로 갱신
- 스테퍼 라벨, ETA 배지 동작(~2초 자동 진행)은 변경 없음

### `/campaigns/[id]` (리포트)

- 상단 상태 배지 유지
- 지표 카드 영역을 3개 카드(노출 수/CTR/예약률, 업계 평균 대비 배지 포함)로 교체
- 퍼널 막대 그래프 섹션 추가(노출→클릭→랜딩 방문→예약)
- 기존 응답 분포(긍정/중립/부정) 섹션 유지 — Figma에는 없지만 우리 제품의 핵심 신호이므로 제거하지 않는다
- "예약자 리스트" 테이블 추가(이메일 목록)
- 하단 CTA: `데모 데이터 초기화` / `새 캠페인 만들기` → `새 프로젝트 만들기`

### `/p/[slug]` (공개 랜딩)

- 기존 3지선다 응답 제출 뒤, 선택적 이메일 입력 단계 추가(건너뛰기 가능)
- 나머지 구조 변경 없음

## 6. 데이터 계약 변경 (추가적)

`lib/contracts/campaign.ts`에 데모 전용 지표 타입 추가:

```ts
export type CampaignDemoMetrics = {
  impressions: number;
  clicks: number;
  landingVisits: number;
  reservations: number;
  ctr: number; // 0~1
  reservationRate: number; // 0~1
  industryBenchmark: {
    ctr: number;
    reservationRate: number;
  };
};
```

`CampaignSpec`에 선택적으로 추가:

```ts
type CampaignSpec = {
  // ...기존 필드
  demoMetrics?: CampaignDemoMetrics; // 없으면 리포트가 지표 카드를 렌더링하지 않음(구버전 spec 호환)
};
```

`lib/contracts/repository.ts` 확장:

```ts
export type SignalInput = {
  campaignId: string;
  visitorId: string;
  optionId: SignalOptionId;
  email?: string; // 추가 — 없으면 기존과 동일하게 동작
};

export interface CampaignRepository {
  // ...기존 메서드 변경 없음
  listReservationEmails(campaignId: string): Promise<string[]>; // 추가
}
```

`FixtureCampaignRepository`는 `recordSignal`에서 `email`이 오면 별도 목록에 저장하고, `listReservationEmails`로 조회 가능하게 한다. 서버 프로세스 메모리 저장(기존 방식과 동일), 실제 DB·이메일 서비스 연동 없음.

## 7. 문서 정합화

이 설계를 구현하면서 다음 문서를 함께 갱신한다:

- `docs/spec.md`: "이메일 등 개인정보를 받지 않는다" 문구 수정, P0-4 완료 기준에 이메일 선택적 수집 반영, 리포트 관련 지표 설명 추가
- `docs/decisions/0001-close-the-validation-loop.md`, `docs/decisions/0006-publish-without-output-review-screens.md`: 이메일 미수집 결정이 이번에 번복됐음을 각 문서에 후기(addendum) 형태로 남긴다(과거 결정 자체를 삭제하지 않고, 왜 바뀌었는지 기록) — 필요하면 신규 ADR(`0008-follow-designer-ad-metrics-and-email-capture.md`)로 분리해도 된다. 구현 시점에 판단.
- `docs/user-flow-and-wireframes.md`: 공개 랜딩 흐름에 선택적 이메일 단계 추가
- `docs/demo-runbook.md`: 리허설 스텝에 이메일 입력(또는 건너뛰기) 단계 추가

## 8. 프로세스 · 리스크

- `lib/contracts/`, `lib/demo/fixtureRepository.ts`는 B 담당 영역과 겹친다. 구현 직전에 `origin/main`을 다시 확인해 B가 이미 겹치는 작업을 하지 않았는지 확인한다(이전에 실제로 한 번 충돌했던 이력이 있다).
- 변경은 전부 추가적(additive)으로 설계했으므로(선택적 필드, 새 메서드), 기존 계약을 사용하는 코드가 깨지지 않아야 한다 — 구현 후 `pnpm check`·`pnpm build`·`pnpm test:e2e`로 회귀를 확인한다.
