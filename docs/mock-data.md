# 목데이터 관리

상태: 구현 전 계획

## 기준 fixture

발표 기본 캠페인은 `마감한입`이다. 마감 전 남는 메뉴를 이웃에게 알리고 싶은 동네 1인 카페 사장님의 문제를 검증한다.

이 입력을 선택한 이유:

- 대상 사용자와 반복 업무를 짧게 설명할 수 있다.
- 랜딩, 인스타그램 카드와 선택형 응답을 한 화면에서 이해하기 쉽다.
- 의료·금융처럼 잘못된 효능 표현의 위험이 큰 분야가 아니다.
- 문제 해결 효과를 사실로 단정하지 않고 사용 의향만 물을 수 있다.

구현을 시작하면 fixture 원본을 `lib/demo/demo-campaign.ts` 한 곳에서 관리한다. 현재 해당 파일과 mock 코드는 존재하지 않으며 화면별로 같은 문구를 복사하지 않는다는 기준만 확정했다.

## 수정 절차

1. `demoIdeaInput`의 아이디어, 고객, 신호 유형과 톤을 수정한다.
2. `demoCampaign`의 검증 가설과 반증 조건을 먼저 맞춘다.
3. 공유 필드 `project.name`, `messaging.valueProposition`, `messaging.hooks[0]`, `validation.signal`을 확정한다.
4. 랜딩과 캐러셀의 보조 문구를 같은 가설에 맞춘다.
5. `safety.claimsToReview`에 검증되지 않은 효과를 적는다.
6. 구현 후 가장 가까운 단위 테스트로 Zod 계약을 확인한다.
7. 구현 후 초기화 동작으로 브라우저에 저장된 이전 fixture를 지운다.

## seed 응답

향후 mock repository는 발표 시작 상태에 익명 seed 응답 2건을 포함한다.

- 긍정 1건
- 중립 1건

화면은 이를 `데모 데이터`로 표시해야 한다. 발표 중 제출하는 한 건도 실제 사용자 조사로 주장하지 않는다. 초기화하면 seed 2건과 `nextAction: null` 상태로 돌아간다.

## OpenAI 연결 후 회귀 입력

G4에서는 아래처럼 구조가 다른 입력 세 개로 스키마와 한글 길이를 확인한다.

1. 마감 전 남는 메뉴를 알리고 싶은 1인 카페 사장님
2. 예약 취소 자리를 다시 알리는 동네 1인 공방 운영자
3. 반복 문의 때문에 수업 준비가 끊기는 독립 강사

이 목록은 실제 수요가 확인됐다는 뜻이 아니라 생성 계약을 검증하기 위한 테스트 입력이다.
