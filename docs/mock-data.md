# 목데이터 관리

상태: 구현 완료

## 기준 fixture

발표 기본 캠페인은 `마감한입`이다. 마감 전 남는 메뉴를 이웃에게 알리고 싶은 동네 1인 카페 사장님의 문제를 검증한다.

이 입력을 선택한 이유:

- 대상 사용자와 반복 업무를 짧게 설명할 수 있다.
- 랜딩, 인스타그램 카드와 선택형 응답을 한 화면에서 이해하기 쉽다.
- 의료·금융처럼 잘못된 효능 표현의 위험이 큰 분야가 아니다.
- 문제 해결 효과를 사실로 단정하지 않고 사용 의향만 물을 수 있다.

fixture 원본과 reference template 3종은 `lib/demo/demo-campaign.ts`에서 관리한다. `lib/demo/demoCampaign.ts`는 기존 import를 위한 하위 호환 shim이다. `/new` 생성기는 이 fixture를 그대로 반환하지 않는다. 키워드는 Figma 템플릿·색상 선택에만 사용하고, 중립 문장 골격에 입력한 상품명·핵심 특징과 문제·솔루션을 주입한다. 이름이 명시되지 않으면 `새 시장검증 캠페인`, 특징이 부족하면 업종과 무관한 안전한 기본 특징으로 보완한다. 화면별로 문구를 복사하지 않고 랜딩, 캐러셀, 게시 문구와 신호 질문이 모두 같은 `CampaignSpec`을 읽는다.

입력과 산출물의 핵심 매핑은 다음과 같다.

- 솔루션의 `제품/서비스 이름`: `project.name`
- 솔루션의 `핵심 특징` 세 항목: `landing.benefits[].title`
- 제품 배경: `validation.problem`과 문제 카드·캐러셀 Problem
- 솔루션 원문: `validation.solution`, 한 줄 설명과 Hero 보조 문구
- 위 필드에서 파생한 후킹·캡션·해시태그: 랜딩, 캐러셀과 `Meta 게시 준비` 공통 사용

각 fixture는 Figma 산출물 템플릿 선택도 함께 고정한다.

- `마감한입`: `cover-31`, `intro-1`
- `동네공방 빈자리`: `cover-32`, `intro-6`
- `클래스 문의형`: `cover-34`, `intro-7`

템플릿 ID는 `CampaignSpec.templates`에 저장되며 브랜드 tone에서 추론하지 않는다. OpenAI adapter를 연결할 때도 지원 목록 밖의 ID는 Zod 검증에서 거절한다.

## 수정 절차

1. `demoIdeaInput`의 아이디어, 고객, 신호 유형과 톤을 수정한다.
2. `demoCampaign`의 검증 가설과 반증 조건을 먼저 맞춘다.
3. 공유 필드 `project.name`, `messaging.valueProposition`, `messaging.hooks[0]`, `validation.signal`을 확정한다.
4. 랜딩과 캐러셀의 보조 문구를 같은 가설에 맞춘다.
5. `safety.claimsToReview`에 검증되지 않은 효과를 적는다.
6. 가장 가까운 단위 테스트로 Zod 계약을 확인한다.
7. 결과 화면의 초기화 동작으로 서버 메모리의 추가 응답과 판단을 seed 상태로 되돌린다.

## seed 응답

mock 저장소는 발표 시작 상태에 익명 seed 응답 4건을 포함한다.

- 긍정 2건
- 중립 1건
- 부정 1건

발표 중 긍정 응답 한 건을 제출하면 사전 기준인 응답 5개 중 긍정 3개에 도달한다. 화면은 이를 `데모 데이터`로 표시하며 발표 중 제출한 응답도 실제 사용자 조사로 주장하지 않는다. 초기화하면 seed 4건과 `nextAction: null` 상태로 돌아간다.

## OpenAI 연결 후 회귀 입력

G4에서는 아래처럼 구조가 다른 입력 세 개로 스키마와 한글 길이를 확인한다.

1. 마감 전 남는 메뉴를 알리고 싶은 1인 카페 사장님
2. 예약 취소 자리를 다시 알리는 동네 1인 공방 운영자
3. 반복 문의 때문에 수업 준비가 끊기는 독립 강사

이 목록은 실제 수요가 확인됐다는 뜻이 아니라 생성 계약을 검증하기 위한 테스트 입력이다.
