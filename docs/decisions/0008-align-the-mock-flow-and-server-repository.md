# ADR-0008: Figma 2단계 흐름과 서버 fixture 저장소를 통합한다

상태: 채택
날짜: 2026-08-25

## 배경

전달된 Figma는 배경과 솔루션을 입력한 뒤 별도 승인 화면 없이 진행 상태로 이동한다. 초기 mock은 응답과 다음 판단을 브라우저 `localStorage`에 저장해 Route Handler와 이후 Supabase repository 경계를 검증하지 못했다. 화면 브랜치와 fixture API 브랜치를 합치면서 하나의 발표 경로와 실패 동작을 확정해야 했다.

## 결정

- `/new`는 배경과 솔루션을 받는 2단계로 유지하고 두 번째 제출에서 `/api/generate`와 `/api/campaigns`를 순서대로 호출한다.
- Figma에 없는 별도 가설 승인 화면은 발표용 mock에서 제거한다. 시장성을 판정하는 일은 자동화하지 않고 응답 뒤 `계속 검증`, `메시지 수정`, `보류`를 사람이 선택한다.
- `CampaignSpec`은 모든 결과물의 단일 계약으로 유지하고 fixture generator도 Route Handler의 입력·Zod 검증을 지난다.
- 캠페인, 응답과 다음 판단은 `CampaignRepository` 뒤의 Node.js 프로세스 메모리에 저장한다. 브라우저에는 중복 확인용 무작위 `visitorId`와 자신이 만든 캠페인의 draft 소유 토큰만 둔다.
- 새 게시마다 고유 id와 slug를 발급하고 같은 입력의 재시도에는 동일한 draft ID와 생성 결과를 사용한다.
- `/campaigns/[id]`와 `/p/[slug]`를 id·slug 조회로 구분하고 공개 경로를 게시 결과에서 파생한다.
- 리포트는 서버 초기 집계로 렌더링하고 focus, 가시성 변경과 2초 polling으로 공개 응답을 갱신한다. 요청 순서를 기록해 늦게 도착한 과거 GET이 저장·초기화 결과를 되돌리지 못하게 한다.
- 응답·판단·초기화 요청이 실패하면 성공 상태를 보여주지 않고 재시도 가능한 오류를 표시한다.

## 기각한 대안

### 제거된 승인 화면을 유지한다

사전 검토에는 유리하지만 확정된 Figma 흐름과 발표 단계 수에 맞지 않는다. live 생성의 사실 검토 정책은 OpenAI adapter를 연결할 때 별도 실패·안전 요구로 검증한다.

### 브라우저 저장소를 계속 사용한다

빠르지만 내부 API와 repository 계약이 장식에 그치고 다른 탭의 실제 서버 집계를 검증할 수 없다.

### 바로 Supabase를 연결한다

다중 기기와 배포에는 필요하지만 계정·키·네트워크 실패가 발표용 P0를 막을 수 있다. 먼저 같은 인터페이스의 fixture 저장소로 Task 13을 고정하고 내일 adapter만 교체한다.

## 결과

- 외부 키 없이도 생성, 게시, 공개 조회, 중복 응답, 집계, 판단, 초기화와 ZIP 다운로드가 실제 내부 API를 통과한다.
- 같은 Node.js 프로세스에서는 여러 브라우저가 상태를 공유하지만 재시작과 serverless 인스턴스 전환에는 유지되지 않는다.
- Vercel에서 여러 기기의 응답을 받기 전에는 `CampaignRepository`를 Supabase로 교체해야 한다.
- 발표용 reset은 live 환경에서 팀 소유 테스트 캠페인으로 제한한다.
